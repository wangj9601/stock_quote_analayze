## 引入 Alembic 管理数据库迁移

- **背景**：原迁移方式为 84 个手写 `migrations/*.py` + `scripts/run_recent_migrations.py`（按文件 mtime 排序执行），无版本账本、无回滚、顺序不可靠。`alembic==1.13.1` 早已在根 `requirements.txt` 中但从未配置。
- **新增文件**：
  - `alembic.ini`（根，**必须纯 ASCII** —— alembic 1.13.x 用系统 locale 编码读该文件，zh-CN Windows 下为 GBK，中文注释会 `UnicodeDecodeError`）
  - `alembic/env.py`、`alembic/script.py.mako`、`alembic/README.md`
  - `alembic/versions/0001_baseline.py`（no-op 基线）
  - `alembic/schema_snapshot_0001.json`（基线时刻 171 张表的结构快照，归档参考）
  - `scripts/db_migrate.py`（封装：status/check/upgrade/downgrade/stamp/revision/history/sql）
  - `docs/database/Alembic_guide.md`（主文档）、`migrations/README.md`（冻结说明）
- **改动的既有文件**：`backend_api/requirements.txt`（启用 alembic）、`backend_api/requirements-minimal.txt`（注释说明 alembic 刻意不入最小依赖）、`scripts/run_recent_migrations.py` 与 `.ps1`（加弃用提示）、`docs/README.md`（加 database/ 索引）。
- **三个必须牢记的坑（关键结论）**：
  1. **两套 ORM Base 且不能传 metadata 列表**：`backend_api.models.Base`(125 表) 与 `backend_core.database.db.Base`(9 表) 有 4 张同名表（`watchlist`/`historical_quotes`/`ma_indicators`/`macd_indicators`）。Alembic 的 `AutogenContext.table_key_to_table` 遇跨 metadata 同名表直接抛 `ValueError`。解决：`MetaData.to_metadata()` 合并为**单一** MetaData，api 侧优先 → 130 表。
  2. **库里 44 张表无 ORM 声明**（当年手写 SQL 建的）：autogenerate 会生成 `drop_table`，执行即不可逆丢数据。解决：`env.py:include_object()` 默认「只增不减」（跳过 `reflected and compare_to is None` 的对象），用 `ALEMBIC_ALLOW_DROP=1` 才放开。实测 upgrade 段 `drop_table`/`drop_column` 计数为 0。
  3. **ORM metadata 与真实库有系统性偏差**：`String()` vs `TEXT`、`Integer` vs `BIGINT`、`JSON` vs `JSONB` → 353 处 `alter_column` 属**伪漂移**；另有 164 `create_index`、14 `create_foreign_key`、6 `create_unique_constraint`、3 `create_table`。**结论：本项目必须手写 revision，autogenerate 只当线索，不可原样提交。**
- **验证（全部通过）**：`stamp 0001_baseline` 对既有库生效（171→172 张，仅多 `alembic_version`）；端到端 `upgrade`→建表→版本 `0002_smoke`，`downgrade -1`→撤销→回 `0001_baseline`，库复原；`db_migrate.py status` 口令脱敏为 `postgres:***@…`；离线 `sql` 子命令正常。
- **其他记忆点**：`backend_api/models` 是**包**（与 `models.py` 同名），`Base` 由包内 importlib 动态载入 `models.py`；`backend_api/database.py` 在模块级 `print` 含明文口令的连接串，脚本里需吞 stdout。

## 把 init_db.py 改造为 Alembic 统一引导入口

- **目标**：`init_db.py` 从「`create_all` + 盲跑 `migrations/*.py`」改为「按库现状自动决策」的引导器，合并原来「建表 + 手工 stamp」两步。
- **状态机（核心设计）**：以 `alembic_version` 表为唯一事实来源，三种分支同一条命令：
  - 账本存在 → `alembic upgrade head`（幂等）
  - 无业务表（空库）→ `create_all`(125) → 历史脚本 → **校验关键表**（不过则中止且**不写账本**）→ `stamp 0001_baseline` → `upgrade head`
  - 有业务表无账本（既有库）→ **仅 stamp**，不执行任何 DDL
- **CLI**：保留 `--status/--verify/--dry-run/--migration-dir`，新增 `--stamp/--rollback/--no-legacy/--strict-legacy/--yes`；`--force` 保留但已废弃。原 `--rollback` 的「尚未实现」现已实现（`alembic downgrade -1`）。
- **API 用法（重要）**：`alembic.config.Config(str(PROJECT_ROOT/"alembic.ini"))` + `cfg.set_main_option("script_location", ...)` 全部绝对化，与 cwd 无关；`command.stamp/upgrade/downgrade` 经 `_run_alembic()` 调用，**之后必须 `setup_logging(force=True)`** —— 因为 `env.py` 的 `fileConfig` 会把 root 级别压到 WARNING 并换掉 handler，不恢复则后续 INFO 日志全丢。当前 revision 用 `MigrationContext.configure(opts={"version_table": ...})` 直读，不经过 env.py（便宜且无副作用）。
- **发现并修复两个历史 bug（`exec` 注入缺失）** —— 原来初始化库**从未成功过**：
  1. 缺 `__file__`：82 个脚本靠 `dirname(dirname(abspath(__file__)))` 定位项目根 → `NameError`；另有 2 个读 `Path(__file__).parent/"sql"/*.sql`（`migrations/sql/` 下 5 个 .sql 确实在用）。
  2. 缺 `__name__`：**84/84 个脚本**都是 `if __name__ == "__main__": main()`。必须设为 **`"__main__"`**；设成模块名会**静默空转**（不报错但不建表），完全不设则 `NameError`。
  3. 另需单独捕 `SystemExit`（5 个 argparse 脚本形如 `raise SystemExit(main())`）；`SystemExit` 不是 `Exception` 子类，不接住会冲出整个引导。
- **实测结果（用独立临时库 `stock_analysis_initdb_test`，已删）**：
  - 空库 `--no-legacy`：125 张 ORM 表 + stamp，退出码 0；复跑判定「已纳管且最新」→ 幂等。
  - 空库含历史脚本：**64/84 成功**，业务表 **144** 张。
  - 既有库纳管（删 `alembic_version` 后）：125 张表**原样**，仅写账本。
  - **144 vs 既有库 171**：差额 30 张以**采集器运行时自建**为主 —— `weekly_quotes`(`weekly_collector.py`)、`industry_board_basic_info`(`realtime_stock_industry_board_ak.py`)、7 张 `*_collect_operation_logs`；少数在 `manual_scripts/`（如 `pvfrs_monitor_metrics`）。**不是引导失败**。反向多出 3 张（`one_yang_three_lines_signals`/`system_alert_rules`/`system_performance_reports`）是 ORM 有、真实库没有的既有漂移，`create_all` 会建出来。
  - 20 个失败的三类原因：argparse 缺人工参数（SystemExit）、依赖采集器运行时建的表（UndefinedTable）、ORM 已建表导致种子数据 NotNullViolation。`migrations/` 按文件名排序执行本身有依赖顺序问题（`add_cn_close_workflow_extra_nodes.py` 排在建表的 `add_collection_workflow_tables.py` 之前）——**故未加多轮重试，性价比太低**。
- **口径修正**：`create_all` 建的是 **125** 张（`backend_api.models.Base`），130 是两套 ORM **合并后**的 metadata 表数。旧文档里写成 130 是混了。
- **口令处理**：`init_db.py` 模块级 import 用 `_suppress_stdout()` 包住，消除 `backend_api.database` 的明文连接串打印；`--status` 显示 `postgres:***@localhost:5446/…`。
- **顺带修**：`backend_api/start.py` 原 `from backend_api.database import init_db` 是**死代码**（`backend_api/database.py` 里没有 `init_db`），ImportError 兜底成空操作 → 数据库从未初始化。已改为委托根部 `init_db.main(["--yes"])`，并支持 `SKIP_DB_INIT=1` 跳过；`sys.path` 同时插入项目根与 `backend_api/`（原来只插 `backend_api/`）。
- **文档同步**：`alembic/README.md`（并修掉指向不存在的 `Alembic迁移指南.md` 的链接）、`alembic/versions/0001_baseline.py`、`migrations/README.md`、`docs/database/Alembic_guide.md`（新增 §1 双入口分工、§2 三者分工表、§4.1 引导决策逻辑与 144/171 表数分析、§4.2 两个 bug、§9 速查行、§10.2/10.3 验证记录、FAQ 4 条）。
- **真实库未受影响**：仍 172 张（171 业务 + 账本），revision `0001_baseline`。

- **完全不存在**（无表/无采集器/无接口）：筹码分布（cyq/chip）、股东户数/十大流通股东/机构持仓/解禁、融资融券/大宗交易/北向资金、逐笔成交落库。
- **关键字段事实**：
  - `stock_fund_flow_daily` 只有 `inflow_amount/outflow_amount/net_amount/turnover_amount/turnover_rate/current_price`，**无超大单/大单分档**；分档只在 `board_fund_flow_daily` 有，但 3 335 行里仅 **65 行** `super_large_net_inflow` 非空。
  - **`historical_quotes.volume` 单位是「手」，`amount` 是「元」⇒ `amount/volume/100 ≈ close`**（实测 15 日比值 0.97~1.02）。这是本项目反推当日 VWAP 的正确公式，易踩坑。
  - `historical_quotes.turnover_rate` 填充率仅 **17.2%**（近一年 143.6 万行 / 74.4 万行有值）—— 这是做筹码分布模型（CYQ）的**唯一硬障碍**；回填采集器 `backend_core/data_collectors/akshare/historical_turnover_rate.py` 已存在，但默认只回溯 30 天且 `SCHED_AKSHARE_TURNOVER_ENABLED=false`（`main.py:332`）。
- **可用方法（已实测算例）**：`主力成本重心 = Σ(net_amount>0 日 net_amount × VWAP) / Σ(net_amount>0 日 net_amount)`，VWAP 用上面公式。实测 300750 宁德时代 316.93（较最新价浮盈 10.49%）、688008 澜起科技 207.89（浮亏 2.21%）、600900 长江电力 28.29（浮亏 0.31%）。
- **现有价位类工具**：`backend_core/analysis/volume_profile.py`（POC/VAH/VAL + 24 桶，日线 `[low,high]` **均匀摊量、无换手衰减**，前端在「价格行为 → 阻力支撑位」展示）；`backend_core/utils/infinite_cost_calculator.py`（CYC∞ **单条线**，非通达信 COST）；RPE 量能加权 KDE（`frontend/js/kde_levels_tool.js`）。三者都是「成交量在哪个价位聚集」的近似，**不等于主力成本**。
- **方法论固有局限（写进结论，非缺数据）**：①「主力」是按单笔金额分档的**推断**，A股无法确知账户归属；② `net = 流入-流出`，「净额大」不等于「买得多」；③ 加权均价只是净流入日的价格重心，卖出部分未扣除；④ 资金流链路未接复权（`stock_adj_factor` / `apply_qfq_to_bars` 存在但未接）；⑤ 15 日样本统计不显著。
- **补齐路线**：A（推荐，零新增外部数据）开启换手率回填 → 实现 CYQ 筹码分布（三角形摊量 + 换手衰减）；B 补个股资金流分档与历史回补（东财 `stock_individual_fund_flow` 有日度历史与 4 档，`stock_fund_flow.py:66` `GET /today` 已在用但只取 2 个数未落库）；C 补席位与逐笔（成本最高）。

## 梳理「生产环境如何执行 Alembic」并写成服务器可用文档

- **问题**：用户问「每次新建表后，生产环境如何执行 Alembic」。经查代码，结论是**必须手工执行，发布链路不跑迁移**。
- **关键事实（核实自代码，非推测）**：
  1. `scripts/deploy/release.ps1:1086-1089` 的迁移步骤是 `if (Test-Path 'migrate_db.py') { python migrate_db.py }`，而**仓库里没有 `migrate_db.py`** → 该分支永不触发。
