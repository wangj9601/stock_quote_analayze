# 历史行情汇总逐级累加改造计划

## 现状

- **当前逻辑**：周线由日线聚合；月线、季线、半年线、年线均由**日线表**分别 resample 生成（见 [多周期行情数据采集系统设计文档](docs/多周期行情数据采集系统设计文档.md)）。
- **数据流**：日线 → 周线（已有）；日线 → 月/季/半年/年（待改为上一级表累加）。

## 目标数据流

```mermaid
flowchart LR
  Daily[日线] --> Weekly[周线]
  Weekly --> Monthly[月线]
  Monthly --> Quarterly[季线]
  Quarterly --> SemiAnnual[半年线]
  SemiAnnual --> Annual[年线]
```



- **月线**：从 **周线表** 累加（`weekly_quotes` / `hk_weekly_quotes`）
- **季线**：从 **月线表** 累加（`monthly_quotes` / `hk_monthly_quotes`）
- **半年线**：从 **季线表** 累加（`quarterly_quotes` / `hk_quarterly_quotes`）
- **年线**：从 **半年线表** 累加（`semiannual_quotes` / `hk_semiannual_quotes`）

## 每类采集器的统一改动

对每个文件只改「单只股票生成」核心方法（如 `generate_single_stock_monthly_data`）及与之相关的查询日期扩展逻辑，其余（表结构、`get_stock_list`、批量入口、命令行）保持不变。

### 1. 月线采集器（A股 + 港股）

- **数据源**：`SELECT date, open, high, low, close, volume, amount, name FROM weekly_quotes`（A股）/ `hk_weekly_quotes`（港股），`WHERE code = :code AND date >= :start_date AND date <= :end_date`。
- **重采样**：保持 `resample('ME')`，聚合规则不变：open=first, high=max, low=min, close=last, volume=sum, amount=sum；name 取 `'first'`（周线表有 name）。
- **查询日期扩展**：当前月线为“当前月”会多取约 40 天日线；改为周线后，建议 `query_start_date = start_date - 35 天`（约 5 周）即可。
- **collected_source**：由 `generated_from_daily` 改为 `generated_from_weekly`。
- **文档注释**：文件头与类注释改为「基于周线数据生成月线」。

### 2. 季线采集器（A股 + 港股）

- **数据源**：从 `monthly_quotes` / `hk_monthly_quotes` 读取相同字段。
- **重采样**：保持 `resample('QE')`，聚合规则同上，name 取 first。
- **查询日期扩展**：由「前 120 天日线」改为「前约 90 天」（约 3 个月）以多取 1 个月便于 resample。
- **collected_source**：改为 `generated_from_monthly`。
- **文档注释**：改为「基于月线数据生成季线」。

### 3. 半年线采集器（A股 + 港股）

- **数据源**：从 `quarterly_quotes` / `hk_quarterly_quotes` 读取。
- **重采样**：保持 `resample('6ME')`，聚合规则同上，name 取 first。
- **查询日期扩展**：由「前 200 天日线」改为「前约 180 天」（约 2 个季度）。
- **collected_source**：改为 `generated_from_quarterly`。
- **文档注释**：改为「基于季线数据生成半年线」。

### 4. 年线采集器（A股 + 港股）

- **数据源**：从 `semiannual_quotes` / `hk_semiannual_quotes` 读取。
- **重采样**：保持 `resample('YE')`，聚合规则同上，name 取 first。
- **查询日期扩展**：由「前 400 天日线」改为「前约 365 天」（约 2 个半年）。
- **collected_source**：改为 `generated_from_semiannual`。
- **文档注释**：改为「基于半年线数据生成年线」。

## 实现要点

- **日期格式**：周/月/季/半年表 date 字段与日线一致（YYYY-MM-DD 或 YYYYMMDD），现有 `normalize_date` 与 `pd.to_datetime` 逻辑可复用。
- **空数据**：若某只股票在源表中无数据，保持现有行为：`if not rows: return True`（视为跳过，不记失败）。
- **依赖顺序**：定时任务已按「周 → 月 → 季 → 半年 → 年」顺序排布时间（如 16:25 周线、16:30 月线…），无需调整。
- **A股/港股一致性**：同一周期 A 股与港股仅数据源表名、股票列表表（stock_basic_info vs stock_basic_info_hk）不同，逻辑完全对称。

## 风险与注意

- **首跑前需有上游数据**：月线依赖周线已存在、季线依赖月线已存在等；若某市场曾只跑过年线而未跑半年线，需先补跑半年线再跑年线。
- **历史全量**：若需对历史区间全量重算，仍通过各脚本的 `generate_*_data(start_date, end_date)` 或命令行传入日期即可；仅数据源和 query_start_date 的扩展量按上表调整。

## 采集性能优化空间

在「逐级累加」改造本身已经带来明显收益（读入行数减少、resample 数据量变小）的前提下，仍有以下可选的进一步优化方向。

### 已具备的收益（本次改造）

- **月线**：由读约 22 条/月日线改为约 4～5 条周线，I/O 与 DataFrame 规模显著下降。
- **季/半年/年**：同理，从上一级表累加后读取行数成倍减少，计算量下降。

### 可选的进一步优化


| 方向           | 说明                                                                                                                                                                                      | 收益                                          | 实现复杂度                                     |
| ------------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------- | ----------------------------------------- |
| **批量查询**     | 一次 `WHERE code IN (:codes)` 拉取多只股票的源表数据，再在内存按 `code` 分组、逐只 resample 后写入。可参考 [hk_historical.py](backend_core/data_collectors/akshare/hk_historical.py) 中按 500 只一批的 `code_batches` 预加载方式。 | 将「每只股票一次 SELECT」变为「每批一次 SELECT」，大幅减少 DB 往返。 | 中：需调整批量入口，按批拉取、分组、再逐只写入。                  |
| **批量提交**     | 当前为每只股票 `commit()` 一次。可改为每处理 N 只股票（如 50～200）或每累计 M 条 INSERT 后提交一次，失败时对当前批 rollback。                                                                                                     | 减少事务与磁盘同步次数，有利于 SQLite/PostgreSQL 等。        | 低：仅改 commit 节奏，注意错误时只回滚当前批。               |
| **批量写入**     | 单只股票多行用 `executemany()` 或单条 INSERT 多值（如 SQLite `INSERT INTO t VALUES (...), (...), ...`）替代循环内多次 `execute(INSERT...)`。                                                                   | 减少与数据库的交互次数。                                | 低～中：需把当前「逐行 execute」改为拼参数列表再 executemany。 |
| **当前周期仅算当前** | `generate_current_*_data()` 仅计算并 upsert「当前月/当前季/当前半年/当前年」一条记录，而非整段区间全量重算。需单独限定查询日期范围与 resample 结果只取最后一条。                                                                                | 定时任务日常跑时只写最少行数，速度最快。                        | 中：需在「当前周期」分支里用不同日期范围与只取末期的逻辑。             |
| **源表索引**     | 确保周/月/季/半年表在 `(code, date)` 上有索引（当前多为 PRIMARY KEY，已覆盖）。若使用 PostgreSQL 且表很大，可显式 `CREATE INDEX`。                                                                                          | 大批量或按区间查询时加速。                               | 低：多数情况 PK 已够用，仅在大表或非 PK 查询时补索引。           |
| **并行处理**     | 多进程/多线程按股票分段处理，每进程独立 Session。                                                                                                                                                           | 多核利用率高，总墙钟时间可能明显缩短。                         | 高：需处理连接池、会话隔离、日志与失败汇总，且与「批量查询」结合时设计更复杂。   |


### 建议实施顺序

1. **先完成逐级累加改造**，观察实际运行耗时与 DB 负载。
2. 若仍觉慢，优先考虑 **批量提交**（改 commit 频率）和 **批量写入**（executemany），改动小、风险低。
3. 再根据需要引入 **批量查询**（按 code 分批拉取、分组 resample），与现有 [hk_historical](backend_core/data_collectors/akshare/hk_historical.py) 的批量预加载模式一致。
4. **当前周期仅算当前** 适合定时任务「只更新最近一根 K 线」的场景，可与 2、3 一起做。
5. **并行处理** 仅在单机多核、股票数量很大且前面手段仍不足时再考虑。
